# Delivery detail

Start with the selected planned work item or bounded issue-only change and its issue/PR evidence. Consult dependencies or overlapping work only when relevant; if no item is selected, make a bounded selection among relevant candidates, not an exhaustive board scan. Inspecting Backlog does not activate its items. Backlog items may already be scoped; a candidate in `docs/delivery-plan.md` is not an activated issue. Select the nearest dependency-ready work item that closes an evidenced gap, coordinate overlapping In Development work, and refine only its selected criteria with the product owner. Multiple In Development items are possible when ownership is coordinated. For planned work, map `Backlog -> In Development -> In Review -> In Verification -> Done`, with failed gates routed to Blocked and a recorded recovery stage, to the board without embedding provider commands in project docs.

For planned product/roadmap deliverable increments, read only the relevant plan row, affected source/nearby tests and bounded detailed requirement entries for its applicable IDs among the 35 original IDs in `docs/requirements.md`. Unplanned documentation or maintenance, including repairs to active authoritative instructions, needs neither a mandatory plan row nor a product requirement ID. Documentation governance repairs may stand alone without either. Locate the exact `#### REQ-... —` heading and read until the next detail heading; consult its register row only if needed. Do not load the whole master, use a coverage/status table, or traverse links automatically. A work item can cover selected criteria of multiple requirements, and one requirement can recur across work items. Link canonical criteria rather than copying definitions. The plan is not evidence of implementation and issue closure is not proof of a whole requirement.

For other domain knowledge, select only the relevant owner through the canonical documentation map in `docs/README.md`. Do not reproduce its routing table here.

Record one checkable outcome, applicable selected IDs and criteria (or a justified `None` for non-product work), scope/exclusions, Given-When-Then examples, dependencies and material security/data/time risks. Inspect the selected item's scope and relevant overlaps first. For a new planned product/roadmap deliverable increment not already represented there, create exactly one GitHub Projects draft item in Backlog, possibly without assignee or issue; obtain human approval of scoped work before activation. Convert that same draft in place via Convert to issue → repository: its distinct Project item ID remains independent of new issue #N. Confirm one linked issue on the same Project item without duplicate card or body. An issue form may also support the bounded issue-only route described below. Apply `status:approved` on the issue reflecting earlier approval; assign the moving actor on the issue. Issue assignees are the source of truth; never independently assign the Project item, invent a separate Project assignee requirement, or assume dynamic moving-actor assignment. Set In Development only after conversion, label and issue assignment are confirmed; if an outcome fails or remains uncertain, stop without claiming activation. Link one or more PRs to that issue: intermediate PRs use `Refs #N`, and the final delivery-ready PR uses `Closes #N` once its pre-merge evidence is review-ready; #N identifies the repository issue, not the Project item. Its closing keyword does not pre-accept the item: a CI-gated Done decision waits for the merged main commit's checks. Reconcile the Project item separately against its evidence; issue auto-closure alone cannot establish Done or acceptance. Activated work cannot bypass its issue with a direct PR. Repository-host actions need separate human authorization. Preserve historical issues and cards unchanged when reassessing current work.

For bounded minor changes, hotfixes, small bugs or an explicitly owner-approved exception, start with an approved repository issue, assign the responsible actor there, then branch and PR without a Project item. The owner may expressly authorize a current issue-only bootstrap before this policy change merges. Record outcome, scope/exclusions, dependencies, risks and verification on the issue; apply `status:approved` before implementation. Do not use this route for an actually new or expanded product/roadmap deliverable increment, regardless of size: use the draft-first conversion route. The issue assignee is the source of truth on either route; a Project Assignees display is not a separate assignment gate. Issue-only work has no Project status, fields or transitions.

For planned work, advance In Development → In Review when a bounded PR is ready for owner review with focused evidence of its selected criteria and checks. For either route, trust successful `gh` mutation output for the entity and result it actually confirms; do not immediately duplicate it with a GET. Query only missing or uncertain results, potentially stale critical state before merge, or asynchronous main CI. A successful PR creation response establishes creation. Apply the required type label and update the branch as needed, then after required PR checks and owner review, obtain an explicit owner order to merge this PR. Immediately before agent squash merge, make a bounded readback of PR identity and issue link, type label, latest head/base, required CI and policy checks, unresolved review threads and mergeability. Do not merge with stale, failed, unresolved or unknown evidence. Fetch only missing evidence separately; fail closed if a mutation outcome is uncertain rather than blindly retrying. Never bypass branch rules. After squash merge, advance planned work In Review → In Verification while required CI for the exact resulting main commit runs. For issue-only work, track pending checks on the issue/PR without inventing board movement. Pending checks do not constitute failure. For documentation or skill-only items, inspect linked content and validation in merged main rather than inventing application behavior. Record current retrospective status honestly; never claim a historical transition that did not occur.

Advance planned work In Verification → Done, or mark issue-only work complete without Project movement, when the agreed selected item outcome and applicable risks are covered and required CI succeeds on the exact resulting main commit. Record item or issue, commit and CI evidence. The explicit owner PR review and merge order conditionally accepted this selected outcome, so no second owner prompt is required. Missing, unknown or pending checks keep planned work In Verification and issue-only work incomplete; pre-merge PR CI and issue closure alone do not suffice. If a pre-merge gate fails, move planned work to Blocked with an actionable reason/link and recovery stage (In Review or In Development), or record the blocked cause and recovery on the issue/PR for issue-only work; fix the existing PR where possible, rerun checks, and seek renewed owner review and merge order. If exact-main CI fails, move planned work to Blocked with run link and recovery stage In Verification, or record failure and recovery on the issue/PR for issue-only work; reopen the same issue, and deliver a corrective PR with `Closes #N`; repeat owner review/order, guarded squash merge and exact-main CI. Keep the original merged PR as history and never revert automatically. Neither failure path treats pending checks as Blocked. Documentation-only Done does not establish product acceptance or REQ-QLT-001 completion. Compare remaining requirement criteria against integrated evidence before claiming a whole requirement accepted; record gaps in the issue/PR, not a status column in the master. Keep a defect in the agreed scope of a still-open issue there; an unplanned bug does not require a `docs/delivery-plan.md` row. For a new bounded defect after delivery, keep any predecessor Project item Done and open a new approved issue linked to the predecessor without rewriting Done history. If the change is a new or expanded deliverable increment, scope a new Backlog draft linked to the predecessor, then approve and convert it through the planned route. This differs from failed exact-main CI on the item still in verification: reopen its same issue. For a genuinely changed product obligation, establish a new requirement ID linked explicitly to the predecessor in the requirements source before planning new work. Never retroactively mutate historical cards.

After merge, retire a local branch only when the PR is confirmed merged, its exact head/content is proven integrated, and all relevant worktrees are clean of tracked and untracked unique work. A squash merge requires PR/content evidence, not ancestry of the original branch tip alone. Linked worktrees containing ignored data cannot be deleted without separate safe preservation; detach or preserve the workspace before retiring its branch. Remote branch cleanup is a separate decision. Never automatically destroy user data.

Update owned documentation only when its knowledge changes. Keep temporary branch names, revision hashes, task/review identifiers and implementation-session narratives out of enduring product docs.
