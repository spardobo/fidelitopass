# Delivery detail

Start with Kanban Active, Review and Verify items: inspect their actual issue/PR evidence, blockers, dependencies and ownership before proposing new work. Backlog items may already be scoped; a candidate in `docs/delivery-plan.md` is not an activated issue. Select the nearest dependency-ready work item that closes an evidenced gap, coordinate overlapping Active work, and refine only its selected criteria with the product owner. Multiple Active items are possible when ownership is coordinated. Map `Backlog -> Active -> Review -> Verify -> Done` to the board without embedding provider commands in project docs.

For planned product work, read only the relevant plan row, affected source/nearby tests and bounded detailed requirement entries for its applicable IDs among the 35 original IDs in `docs/requirements.md`. Unplanned documentation or maintenance, including repairs to active authoritative instructions, needs neither a mandatory plan row nor a product requirement ID. Documentation governance repairs may stand alone without either. Locate the exact `#### REQ-... —` heading and read until the next detail heading; consult its register row only if needed. Do not load the whole master, use a coverage/status table, or traverse links automatically. A work item can cover selected criteria of multiple requirements, and one requirement can recur across work items. Link canonical criteria rather than copying definitions. The plan is not evidence of implementation and issue closure is not proof of a whole requirement.

Record one checkable outcome, applicable selected IDs and criteria (or a justified `None` for non-product work), scope/exclusions, Given-When-Then examples, dependencies and material security/data/time risks. Inspect current board work and scope first. For new work not already represented there, create exactly one GitHub Projects draft item in Backlog, possibly without assignee or issue; obtain human approval of scoped work before activation. Convert that same draft in place via Convert to issue → repository: its distinct Project item ID remains independent of new issue #N. Verify one linked issue and one Project item without duplicate card or body. An issue form, if available, supports the converted content, not a separate starting route. Apply `status:approved` on the issue reflecting earlier approval; assign the moving actor on the issue, then verify through readbacks that the actor appears both in issue assignees and in Project Assignees. Issue assignees are the source of truth and the linked Project display reflects them automatically; never independently assign the Project item or assume dynamic moving-actor assignment. Set Active only after conversion, `status:approved`, assignment and both readbacks succeed; if conversion, label, assignment, status or either readback fails, stop without claiming activation. Link one or more PRs to that issue: intermediate PRs use `Refs #N`, and the final PR uses `Closes #N` only once agreed item evidence is accepted; #N identifies the repository issue, not the Project item. Under board policy or configured built-in GitHub automation on issue closure, move the Project item separately to Done; issue closure alone guarantees neither Done nor acceptance. Activated work cannot bypass its issue with a direct PR. Repository-host actions need separate human authorization. Preserve historical issues and cards unchanged when reassessing current work.

Done requires met item acceptance, proportionate automated checks, integrated behaviour, applicable risk coverage, and product-owner acceptance with QA/developer evidence linked in issue/PR. Documentation-only Done does not establish product acceptance or REQ-QLT-001 completion. Compare remaining requirement criteria against integrated evidence before claiming a whole requirement accepted; record gaps in the issue/PR, not a status column in the master. Keep a defect in the agreed scope of a still-open issue there; an unplanned bug does not require a `docs/delivery-plan.md` row. After closure, keep the predecessor Project item Done; scope a new Backlog draft item linked to the predecessor, then approve and convert it through the same route for a defect or unmet criterion. For a genuinely changed product obligation, establish a new requirement ID linked explicitly to the predecessor in the requirements source before planning new work. Never retroactively mutate historical cards.

Update owned documentation only when its knowledge changes. Keep temporary branch names, revision hashes, task/review identifiers and implementation-session narratives out of enduring product docs.
