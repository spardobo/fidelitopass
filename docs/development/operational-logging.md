# Operational logging contract

Use native Laravel `Log` calls with application-authored event codes and explicit safe context. Native Monolog `JsonFormatter` represents configured records as JSON. This specializes [Structured logging](laravel-application-standard.md#structured-logging); security and domain owners retain their policies. Logs are diagnostic, not a durable audit or proof of browser receipt or customer Wallet save.

## Envelope and trusted input

Configured records use the native Monolog envelope: `message`, `context`, numeric `level`, uppercase `level_name`, `channel`, `datetime` and `extra`. The authored event code is the `message`. `datetime` retains native emission-time formatting and timezone; it is not authoritative domain time. All eight PSR severities use this envelope. Individual records end with a newline; native newline batches separate records without a terminal newline.

Collectors that consumed the former version-1 envelope must read `message` instead of `event` and `datetime` instead of `timestamp`. `level` is now numeric; use `level_name` for severity text. `schema_version` and the fixed `service` field are no longer emitted. Collection/deployment metadata can identify the service.

Declare stable event and reason codes at their callsites, using clear names such as `customer_pass.creation.completed`. There is no event enum, central catalogue or spelling validator. Never use request text, provider messages or credentials as codes.

Context is open metadata, including relevant scalars and nested structures. Callers select explicit nonsecret values; they do not pass whole requests, models, private operation objects, exceptions or arbitrary exception `context()` data. The formatter uses native normalization, not a field registry, domain validator or secret detector. New safe fields need no formatter change. Native `extra` metadata is preserved, so processor inputs must follow the same explicit safe-input contract as shared context.

Native exception stacktrace serialization is enabled in the formatter. It applies when a record contains an exception; it does not synthesize traces for scalar informational logs or authorize raw exceptions at application callsites. The application reporter supplies selected diagnostic frames instead.

Request middleware alone generates and injects correlation UUIDs and ignores incoming correlation headers. Correlation stays internal to logs; no X-Request-ID response header or request correlation attribute is created. Individual events rely on that shared context; they do not accept, generate or supply request identifiers. Logs outside the active middleware scope, including standalone operations and framework reports after unwind, may have no request correlation.

Creation emits completion after confirmed Google creation and local commit, distinguishing issuance from replay and recording provider readback. Readback confirmation uses warning severity. Classified failures retain stage, definitive versus unknown outcome and retry policy. Completion means a private handoff is ready, not that it was received or saved.

Creation failures also retain the caught exception class, using the source database or transport class when available. Database boundaries retain SQLSTATE without keeping SQL, bindings or the original cause. Unexpected creation failures retain the selected throw location and native caller frames under the same field restrictions as the global reporter. Classified failures remain one owner event; they are not reported again.

Provider failures retain the locally selected HTTP method, native exception class and available failure status. A failed confirmation read retains the preceding write method, available failure status and source exception class separately. A transport failure may have no status; keep its exception class without retaining the exception itself. Successful SDK models do not expose an HTTP status; do not invent one. Raw provider bodies, messages, descriptions, metadata, URLs and echoed identifiers are omitted. These diagnostics identify the operation and failure class, not a guaranteed root cause; they do not change retry policy or the public response.

Object binding conflicts retain an application-authored field and mismatch category, never the expected or actual value. Provider-library logs and exceptions are not an alternate raw diagnostic channel. Application boundaries discard sensitive causes before emission; unsafe SDK HTTP debug logging prevents issuance.

Handled settings failures use the global reporter once before safe UI feedback. Missing two-factor setup data remains ordinary absence, not a manufactured exception. Two-factor credential persistence remains retired. Private pass identification keeps its existing SQL-free failure boundary; its generic exception does not retain the database root cause.

## Collection and failures

- Production defaults to stderr and development to rotating files through a native stack. Explicit deployment channels and severity thresholds remain authoritative. An error threshold intentionally drops warnings.
- Single, daily, monthly and stderr handlers emit JSON Lines. Errorlog, syslog and papertrail receive the same formatted object, but collectors may add transport prefixes. Optional Slack sends formatted JSON text without attachments or extra context; it is not a JSON-Lines sink.
- Laravel's own `LogManager` owns channel construction and last-resort emergency behavior. Emergency output does not use the configured JSON formatter and may include raw construction exceptions or text. It is outside the configured envelope and sanitization guarantees, as are pre-bootstrap/platform diagnostics. Validate configured channels and protect collection access; do not assume emergency output is sanitized.
- The stack uses native `ignore_exceptions=false` so destination write failures remain visible. Native emergency construction handles channel-resolution failures, not arbitrary write errors. Log calls have no swallowing catches, custom emergency hook, fallback emitter, deferred path or logging queue.
- A logging failure can propagate, change the HTTP result or interrupt exception reporting. A confirmed domain commit still exists; do not reinterpret a completion-log failure as a failed creation, infer rollback or automatically repeat a provider POST. No delivery guarantee exists if a destination fails.
- Normal Laravel exception eligibility remains authoritative. The global report callback writes one stable event with exception class, source file/line and `exception_frames`, inheriting request correlation only while middleware context is active. It selects only available `file`, `line`, `class` and `function` fields from the complete native caller chain before logging, so native listeners never receive the raw exception. There is no application frame cap or custom path/symbol normalization. Native source paths, closure labels and anonymous class labels remain unchanged for server diagnosis, not customer-facing responses. Reports exclude raw messages, SQL/bindings, request data, arguments, frame objects and chained causes. The source location identifies the actual throw site separately from caller frames; the caller chain does not guarantee a complete root cause. Ordinary informational logs do not acquire exception diagnostics. Returning `false` suppresses Laravel's duplicate raw record when reporting succeeds. Caught creation failures are already classified by their owner and are not reported again by the controller.
- On normal or exceptional unwind, middleware clears all resolved native channel context, flushes manager shared context, then restores only pre-request shared metadata.

Safety depends on explicit callsite inputs and valid configured channels. This is not a complete application callsite audit or general secret-detection system. Arbitrary custom channels and platform direct writes remain outside this contract. Deployment owns retention, permissions and collection.
