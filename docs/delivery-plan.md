# FidelitoPass Delivery Plan

This is the canonical lightweight plan of candidate **work items** with checkable outcomes. Prefer reviewable, vertically scoped outcomes; this is not a Scrum backlog, numbered Waves, a fixed sequence, or proof of delivery. `docs/requirements.md` owns the 35 original stable IDs and their acceptance criteria; ADR-003 governs Promotion-owned extra points and frozen publication terms. The historical CHL prefix still denotes Promotion requirements. References below scope candidate work, not redefine requirements or assign exclusive ownership: a requirement can support multiple items, and an item can support multiple requirements. The board owns progress; this document has no item or requirement status.

Choose the nearest work from dependency evidence and the Kanban board: inspect Active and Review/Verify items first for unfinished integration or blockers; among scoped candidates, select a dependency-ready item that closes a demonstrable gap without duplicating active ownership. Refine its scope with the product owner before activation. If a prerequisite is missing, select that prerequisite rather than forcing every candidate into an issue. Revisit this plan as evidence and priorities change; no candidate is automatically scheduled.

Each demonstration is a checkable outcome, not an additional acceptance contract. Code, tests, and demonstrations support product-owner acceptance against the linked canonical criteria; issue closure alone cannot establish completion of an entire requirement. Cross-cutting UX, security, integrity, reliability, and quality IDs recur where their criteria apply.
